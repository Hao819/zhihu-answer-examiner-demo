# 答主考官｜Demo 设计方案

> **一句话**：你先用自己的话讲，知乎真实答主来当考官，挑出你讲错、讲漏和仍有争议的地方，直到你真正会讲。

**参赛赛道**：知识炼金场：学习工具与知识生产  
**Demo 版本**：Hackathon MVP  
**默认演示主题**：AI 会不会替代初级程序员？  
**视觉参考**：`D:\zhihu_t` 中的刘看山三视图与动态素材

---

## 1. 产品定位

### 1.1 要解决的问题

很多人“看过”知乎回答，却没有真正形成自己的理解。传统 AI 总结会直接给出答案，用户容易产生“我好像懂了”的错觉，却没有经历主动回忆、表达和纠错。

### 1.2 产品承诺

答主考官把学习顺序倒过来：

> **先让用户讲，再用知乎社区的真实观点检验用户。**

最终用户得到的不是一段泛泛总结，而是一份带来源、带争议说明、能看出前后进步的掌握度报告。

### 1.3 目标用户

- 想快速入门一个领域的大学生和职场新人；
- 准备面试、答辩、分享或写作的用户；
- 看过大量知乎内容，但难以整理成自己语言的人；
- 希望把阅读转化为输出的知识型创作者。

---

## 2. 核心体验闭环

```text
选择主题
   ↓
用自己的话讲一遍（文字 / 语音转文字）
   ↓
检索知乎高质量回答与相关问题
   ↓
抽取关键论点、前提、例子和反例
   ↓
逐条比对用户讲述
   ├─ 说对了：确认并显示来源
   ├─ 说反了：引用答主片段并解释冲突
   ├─ 讲漏了：提示关键点和适用条件
   └─ 观点不同：标记为观点差异，不武断判错
   ↓
用户补讲 / 修改
   ↓
生成掌握度报告 + 带来源知识卡片
```

### 2.1 体验原则

1. **先输出，后检索**：避免用户先看答案再“假装会了”。
2. **证据在反馈旁边**：每条判断都能展开看到知乎来源。
3. **区分错误与分歧**：高赞不等于绝对正确，经验也有适用边界。
4. **反馈可行动**：每个遗漏点都给出一句“请补讲……”的任务。
5. **让进步可见**：展示补讲前后掌握度变化。

## 3. Demo 范围（MVP）

### 3.1 必做

- 主题选择（预置 3 个主题，支持自定义）；
- 文本输入用户讲述；
- 知乎内容检索与来源列表；
- 5～10 个关键知识点抽取；
- “准确 / 错误 / 遗漏 / 观点差异”四类比对结果；
- 用户补讲一次；
- 掌握度报告；
- 生成 1 张可复制的知识卡片；
- 每个关键结论保留知乎原文或摘要片段、作者和链接。

### 3.2 可选加分

- 浏览器麦克风录音，自动转文字；
- 刘看山“思考 / 认真 / 鼓励”动态状态；
- 一键生成 5 张复习卡片；
- 导出 Markdown；
- “新手 / 进阶”两种评分标准；
- 用户登录后保存历史报告。

### 3.3 明确不做

- 完整社交关系链；
- 多人实时辩论；
- 大规模个人知识库同步；
- 自动发布知乎内容；
- 伪造答主认证、赞数或完整原文。

## 4. 页面与交互设计

## 4.1 页面 A：选题首页

### 页面目标

让用户在 10 秒内理解产品，并立即开始一次练习。

### 布局

```text
┌──────────────────────────────────────────────┐
│ 知乎 · 答主考官                    [历史报告] │
│                                              │
│       你讲一遍，知乎来挑错                   │
│  别急着看答案。先用自己的话解释一个问题。     │
│                                              │
│  刘看山（考官）     ┌────────────────────┐    │
│   [思考动作]         │ 选择一个主题       │    │
│                      │ [AI 会替代程序员吗]│    │
│                      │ [数据分析怎么入门] │    │
│                      │ [自定义主题……]    │    │
│                      └────────────────────┘    │
│                              [开始考试]        │
└──────────────────────────────────────────────┘
```

### 文案

- 主标题：**你讲一遍，知乎来挑错**
- 副标题：先用自己的话解释，再由真实答主的观点检验你的理解。
- 考官提示：**“别担心，我只挑知识，不挑表达。”**

---

## 4.2 页面 B：自由讲述

### 页面目标

让用户在没有答案提示的情况下完成主动回忆。

### 交互

- 大文本框：建议 150～500 字；
- 可选录音按钮：录音后显示转写文本，用户可编辑；
- 右侧刘看山状态卡：思考动作 + “考官正在记录评分点”；
- 进度提示：`第 1 轮 / 2 轮`；
- 提交按钮：**提交我的讲述**；
- 空内容拦截：至少输入 30 字，避免无意义评分。

### 引导问题（不显示答案）

以“AI 会不会替代初级程序员？”为例：

- 你认为最先被影响的工作是什么？
- 你判断的依据是什么？
- 哪些能力短期内仍然重要？

---

## 4.3 页面 C：答主比对

### 页面目标

把“AI 判断”变成可验证、可理解的反馈。

### 顶部状态

```text
正在对照 8 个关键点        已完成 8 / 8
掌握度 72%                 [查看评分规则]
```

### 关键点卡片

每张卡包含：

- 状态标签：准确 / 需要修正 / 关键遗漏 / 观点差异；
- 用户原话（高亮相关句子）；
- 考官点评；
- 知乎来源：标题、作者、真实返回的互动数据（若有）；
- “查看原文”链接；
- 操作按钮：`我来补讲`。

### 示例卡片

```text
需要修正  ·  因果关系说反了

你的讲述：
“AI 主要会替代需要长期项目经验的复杂工作。”

考官刘看山：
“这点可能说反了。当前更容易被自动化的是规则清晰、
可拆分、反馈周期短的初级任务；复杂工作通常仍需要上下文判断。”

知乎来源：某回答 · 作者认证信息（接口有返回时展示）· 1.2k 赞（接口有返回时展示）
[查看知乎原文]                         [补讲这一点]
```

### 反馈语气

采用“严格事实 + 友好表达”：

- 不说：`你完全错了`；
- 说：`这点与该回答的结论相反，冲突主要在适用条件。`；
- 不说：`你没看懂`；
- 说：`你已经覆盖结论，但还缺少一个重要前提。`

---

## 4.4 页面 D：补讲与复测

### 页面目标

让用户完成一次有针对性的主动修正，而不是只看反馈。

### 交互

- 左栏固定显示待补讲点；
- 右栏输入补讲内容；
- 刘看山从“皱眉思考”切换为“点头”；
- 提交后只重新评估相关知识点；
- 显示前后变化：`该点：待修正 → 已掌握`。

### 补讲提示模板

> 请用自己的话补充：哪些类型的任务更容易被自动化？复杂任务为什么暂时不等于不会被影响？

---

## 4.5 页面 E：掌握度报告

### 页面目标

让结果可复盘、可分享、可继续学习。

### 报告结构

```text
本次掌握度                    91%
补讲前 72%  ───────────────→  补讲后 91%

准确覆盖       6 / 8
需要修正       1 处
关键遗漏       2 处
观点差异       1 处

你已经掌握：……
下一步建议：……
仍需验证：……

[生成知识卡片] [再考一次] [复制分享]
```

### 知识卡片字段

1. 问题；
2. 一句话结论；
3. 关键条件；
4. 常见误区；
5. 不同答主的观点；
6. 我的最终理解；
7. 知乎来源列表。

视觉参考素材：

- 电脑前思考动态：[`docs/assets/liukanshan-thinking.gif`](assets/liukanshan-thinking.gif)

角色定位：**严格、诚实、友好，不制造羞耻感的知识考官**。

### 5.2 状态动作映射

| 状态 | 视觉动作 | 触发时机 | 旁白 |
|---|---|---|---|
| idle | 待机 | 首页等待 | “准备好了吗？” |
| thinking | 电脑前思考 | 检索与比对 | “我正在找能证明这件事的回答。” |
| challenge | 面向用户 | 发现错误或遗漏 | “这里需要再解释一步。” |
| nod | 点头 | 关键点答对 | “这点讲得很清楚。” |
| cheer | 鼓励 | 掌握度提升 | “这次你真的讲明白了。” |

### 5.3 色彩

| 用途 | 色值 | 说明 |
|---|---|---|
| Zhihu 蓝 | `#056DE8` | 主按钮、链接、进度条 |
| 深墨色 | `#1F2329` | 标题与正文 |
| 浅背景 | `#F7F8FA` | 页面底色 |
| 卡片白 | `#FFFFFF` | 内容容器 |
| 准确绿 | `#16A05D` | 已覆盖、已掌握 |
| 修正橙 | `#D97706` | 需要修正、关键遗漏 |
| 差异紫 | `#7C3AED` | 观点差异 |
| 分隔线 | `#E5E7EB` | 边框与分隔 |

### 5.4 组件风格

- 圆角：卡片 16px，按钮 10px；
- 阴影：低对比、柔和，避免“考试系统”压迫感；
- 字体层级：标题 32px，区块标题 20px，正文 15～16px；
- 状态标签使用图标 + 颜色 + 文本，不只依赖颜色；
- 引用片段使用浅蓝背景和左侧 3px 蓝色竖线；
- 刘看山图片保留白色身体、黑色鼻子与四肢的原始特征，不做过度拟人化改造。

## 6. AI 评估逻辑

### 6.1 处理管线

```text
知乎检索结果
   ↓
去重、截断、来源标准化
   ↓
关键点抽取（结论 / 条件 / 例子 / 反例）
   ↓
用户讲述切分为主张
   ↓
主张 ↔ 关键点匹配
   ↓
判断标签 + 证据句 + 修正建议
```

### 6.2 评分建议

每个关键点 0～2 分：

- `2`：结论和关键条件基本准确；
- `1`：方向正确，但缺少条件或例子；
- `0`：明显冲突、概念混淆或完全未覆盖。

总分示例：

```text
基础掌握度 = 已覆盖关键点得分 / 全部关键点满分 × 100%
补讲加分 = 仅对补讲前为 0 或 1 的点重新计算
最终掌握度 = 补讲后得分 / 全部关键点满分 × 100%
```

### 6.3 结构化输出格式

```json
{
  "topic": "AI 会不会替代初级程序员？",
  "score_before": 72,
  "score_after": 91,
  "items": [
    {
      "status": "correction",
      "user_claim": "...",
      "assessment": "因果关系说反了",
      "explanation": "...",
      "source": {
        "title": "回答标题",
        "author": "作者名",
        "url": "https://www.zhihu.com/...",
        "quote_or_summary": "接口真实返回的原文片段或回答摘要"
      },
      "repair_prompt": "请补充说明……"
    }
  ]
}
```

### 6.4 提示词约束

系统提示词应明确：

- 只能根据检索到的知乎内容判断，不得编造来源；
- 区分事实冲突、概念混淆、关键遗漏和观点差异；
- 不能把个人经验写成普遍事实；
- 引用必须逐字来自真实返回片段，拿不到正文时标注“回答摘要”；
- 没有足够证据时使用“可能遗漏”或“观点不同”，不要武断判错；
- 每条反馈都返回对应来源 URL。

## 7. 知乎能力接入建议

### 7.1 MVP 调用组合

- `search zhihu`：按主题检索相关回答、文章和经验；
- `question answers`：用户粘贴具体问题链接时，读取该问题下的回答摘要与链接；
- `hot`：首页提供一个“从今日热榜开考”的入口（可选）；
- `answer`：接口不可用时作为综合解释兜底，但结果必须标记为 AI 生成，不替代知乎来源。

### 7.2 缓存与降级

- 对同一主题的检索结果做短期缓存和请求去重；
- 预置 3 个离线演示主题，保证路演不依赖实时网络；
- 接口失败时显示：`知乎内容暂时不可用，已切换到演示资料`；
- 结果为空时引导用户改写主题，不反复重试；
- 页面显示“来源类型”：原文片段 / 回答摘要 / AI 综合说明。

### 7.3 归属与合规

- 保留作者名、标题和知乎原文链接；
- 不把 AI 改写内容标成答主原话；
- 认证、赞数等字段只有接口真实返回时展示；
- 不在前端、日志、仓库和演示视频中暴露 Access Secret、OAuth Token 等凭证；
- 明示：**高赞回答代表社区观点，不等于绝对事实。**

## 9. 90 秒路演脚本

### 0～10 秒：提出问题

“我们都经历过：看完一篇知乎高赞回答，觉得自己懂了，但让你解释时却讲不清。”

### 10～20 秒：产品亮相

“这是答主考官。你先讲一遍，知乎真实答主来考你。”

### 20～40 秒：用户讲述

选择“AI 会不会替代初级程序员”，现场输入一段有明显缺漏的回答，点击提交。

### 40～65 秒：答主比对

展示 3 张卡片：

1. 一条“准确覆盖”；
2. 一条“因果关系说反了”，展开来源片段；
3. 一条“关键遗漏”，显示答主反复强调的适用条件。

### 65～78 秒：补讲

用户补充“规则清晰、可拆分的任务更易被自动化”，该点从“需要修正”变成“已掌握”。

### 78～90 秒：结果收束

展示 `72% → 91%`，生成带知乎来源的知识卡片。

收尾句：

> “知乎让我们看见真实经验，答主考官让我们证明自己真的理解了。”

## 10. 评委关注点对应

| 评审关注 | Demo 中的证据 |
|---|---|
| 是否真正使用知乎内容 | 每张反馈卡显示知乎来源和原文链接 |
| 是否有学习价值 | 用户先讲、再补讲，掌握度前后变化 |
| 是否有知识生产 | 最终生成用户自己的知识卡片和理解表述 |
| 是否有 AI 创新 | 主张级比对、证据绑定、四类反馈 |
| 是否可落地 | 预置主题、缓存、离线降级、简单技术架构 |
| 是否尊重社区 | 区分原文 / 摘要 / AI 生成，保留作者归属 |

## 12. 后续版本

第一版验证“主动讲述 + 社区校验”是否成立；后续可扩展：

- 个人学习档案与间隔复习；
- 收藏夹自动生成主题课程；
- 多答主观点地图；
- 面试 / 答辩专用考官模式；
- 语音表达质量与逻辑结构反馈；
- 将最终知识卡片发布为用户自己的创作草稿。

**核心原则不变：先让人思考和表达，再让 AI 借助知乎真实知识帮助他修正。**
