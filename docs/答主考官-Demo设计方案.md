# 答主考官｜Demo 产品设计方案

> **一句话**：你先用自己的话讲，知乎社区真实内容与直答来当考官，挑出你讲错、讲漏和仍有争议的地方，直到你真正会讲。

**参赛赛道**：知识炼金场：学习工具与知识生产  
**Demo 版本**：Hackathon MVP  
**默认演示主题**：AI 会不会替代初级程序员？  
**视觉参考**：`D:\zhihu_t` 中的刘看山三视图与动态素材

> **方案修订（v2 · 2026-09-13）**：本方案以“真实知乎搜索 + 知乎直答”为唯一产品运行路径。仓库中的 fixture 只允许用于纯函数单元测试，不得作为页面展示、接口兜底或路演数据。知乎服务不可用时，产品明确提示重试，不伪造来源、不生成离线答案。

---

## 1. 产品定位

### 1.1 要解决的问题

很多人“看过”知乎回答，却没有真正形成自己的理解。传统 AI 总结会直接给出答案，用户容易产生“我好像懂了”的错觉，却没有经历主动回忆、表达和纠错。

### 1.2 产品承诺

答主考官把学习顺序倒过来：

> **先让用户讲，再用知乎社区的真实观点检验用户。**

最终用户得到的不是一段泛泛总结，而是一份带来源、带争议说明、能看出前后进步的掌握度报告。

### 1.3 目标用户

- 想快速入门一个领域的大学生和职场新人；
- 准备面试、答辩、分享或写作的用户；
- 看过大量知乎内容，但难以整理成自己语言的人；
- 希望把阅读转化为输出的知识型创作者。

## 2. 核心体验闭环

产品提供两种入口，按用户已有基础分流：

- **先讲再考**：适合已有一些了解的用户，先主动回忆，再接受知乎校验；
- **从 0 掌握**：适合几乎不了解主题的用户，先由知乎搜索与知乎直答生成入门地图，再用自己的话复述确认。

```text
选择主题
   ├─ 先讲再考 → 用自己的话讲一遍
   └─ 从 0 掌握 → 入门地图 → 用自己的话复述
   ↓
并行调用知乎搜索与知乎直答
   ↓
保留搜索摘要作为可追溯证据，直答作为综合评估说明
   ↓
逐条比对用户讲述
   ├─ 说对了：确认并显示来源
   ├─ 说反了：展示相关搜索摘要并解释冲突
   ├─ 讲漏了：提示关键点和适用条件
   └─ 观点不同：标记为观点差异，不武断判错
   ↓
用户补讲 / 修改
   ↓
生成掌握度报告 + 带来源知识卡片
```

### 2.1 体验原则

1. **先输出，后检索（先讲再考）**：避免用户先看答案再“假装会了”；从 0 掌握模式则先提供最小入门地图，再要求用户复述。
2. **证据在反馈旁边**：每条判断都能展开看到知乎来源。
3. **区分错误与分歧**：高赞不等于绝对正确，经验也有适用边界。
4. **反馈可行动**：每个遗漏点都给出一句“请补讲……”的任务。
5. **让进步可见**：展示补讲前后掌握度变化。
6. **实时数据透明**：明确区分“真实搜索摘要”和“知乎直答综合说明”，服务异常时不以离线资料冒充实时结果。
7. **允许从零开始**：零基础用户先获得定义、框架、条件和例子的最小地图，再进入主动复述，不因“不会讲”而被拒之门外。

## 3. Demo 范围（MVP）

### 3.1 必做

- 主题选择（预置 3 个主题，支持自定义）；
- 两种学习入口：先讲再考、从 0 掌握；
- 文本输入用户讲述；
- 从 0 掌握模式生成 5～8 个由浅入深的入门知识点、常见误区和自测问题；
- 通过知乎 Skill CLI 执行真实知乎内容检索与来源列表；
- 通过知乎直答生成 5～8 个结构化关键知识点；
- “准确 / 错误 / 遗漏 / 观点差异”四类比对结果；
- 用户补讲一次；
- 掌握度报告；
- 生成 1 张可复制的知识卡片；
- 每个关键结论尽量绑定知乎搜索摘要、作者和链接；无法绑定时保留直答说明并明确“未返回可验证链接”。

### 3.2 可选加分

- 浏览器麦克风录音，自动转文字；
- 刘看山“思考 / 认真 / 鼓励”动态状态；
- 一键生成 5 张复习卡片；
- 导出 Markdown；
- “新手 / 进阶”两种评分标准；
- 用户登录后保存历史报告。

### 3.3 明确不做

- 完整社交关系链；
- 多人实时辩论；
- 大规模个人知识库同步；
- 自动发布知乎内容；
- 伪造答主认证、赞数或完整原文。

## 4. 页面与交互设计

## 4.1 页面 A：选题首页

### 页面目标

让用户在 10 秒内理解产品，并根据自己的基础选择“先讲再考”或“从 0 掌握”。

### 布局

```text
┌──────────────────────────────────────────────┐
│ 知乎 · 答主考官                    [历史报告] │
│                                              │
│       你讲一遍，知乎来挑错                   │
│  别急着看答案。先用自己的话解释一个问题。     │
│  [先讲再考]        [从 0 掌握]                  │
│                                              │
│  刘看山（考官）     ┌────────────────────┐    │
│   [思考动作]         │ 选择一个主题       │    │
│                      │ [AI 会替代程序员吗]│    │
│                      │ [数据分析怎么入门] │    │
│                      │ [自定义主题……]    │    │
│                      └────────────────────┘    │
│                              [开始考试]        │
└──────────────────────────────────────────────┘
```

### 文案

- 主标题：**你讲一遍，知乎来挑错**
- 副标题：先用自己的话解释，再由知乎社区观点与直答检验你的理解。
- 零基础入口：**不知道也没关系，先从一张知乎入门地图开始。**
- 考官提示：**“别担心，我只挑知识，不挑表达。”**

---

## 4.2 页面 B：自由讲述

### 页面目标

让用户在没有答案提示的情况下完成主动回忆。

### 交互

- 大文本框：建议 150～500 字；
- 可选录音按钮：录音后显示转写文本，用户可编辑；
- 右侧刘看山状态卡：思考动作 + “考官正在记录评分点”；
- 进度提示：`第 1 轮 / 2 轮`；
- 提交按钮：**提交我的讲述**；
- 空内容拦截：至少输入 30 字，避免无意义评分。

当用户选择“从 0 掌握”时，不进入本页，而是先进入页面 F 的入门地图。

### 引导问题（不显示答案）

以“AI 会不会替代初级程序员？”为例：

- 你认为最先被影响的工作是什么？
- 你判断的依据是什么？
- 哪些能力短期内仍然重要？

---

## 4.3 页面 C：答主比对

### 页面目标

把“AI 判断”变成可验证、可理解的反馈。

### 顶部状态

```text
正在对照 8 个关键点        已完成 8 / 8
掌握度 72%                 [查看评分规则]
```

### 关键点卡片

每张卡包含：

- 状态标签：准确 / 需要修正 / 关键遗漏 / 观点差异；
- 用户原话（高亮相关句子）；
- 考官点评；
- 知乎来源：标题、作者、真实返回的互动数据（若有）；
- “查看原文”链接；
- 操作按钮：`我来补讲`。

### 示例卡片

```text
需要修正  ·  因果关系说反了

你的讲述：
“AI 主要会替代需要长期项目经验的复杂工作。”

考官刘看山：
“这点可能说反了。当前更容易被自动化的是规则清晰、
可拆分、反馈周期短的初级任务；复杂工作通常仍需要上下文判断。”

知乎来源：某回答 · 作者认证信息（接口有返回时展示）· 1.2k 赞（接口有返回时展示）
[查看知乎原文]                         [补讲这一点]
```

### 反馈语气

采用“严格事实 + 友好表达”：

- 不说：`你完全错了`；
- 说：`这点与该回答的结论相反，冲突主要在适用条件。`；
- 不说：`你没看懂`；
- 说：`你已经覆盖结论，但还缺少一个重要前提。`

---

## 4.4 页面 D：补讲与复测

### 页面目标

让用户完成一次有针对性的主动修正，而不是只看反馈。

### 交互

- 左栏固定显示待补讲点；
- 右栏输入补讲内容；
- 刘看山从“皱眉思考”切换为“点头”；
- 提交后只重新评估相关知识点；
- 显示前后变化：`该点：待修正 → 已掌握`。

### 补讲提示模板

> 请用自己的话补充：哪些类型的任务更容易被自动化？复杂任务为什么暂时不等于不会被影响？

---

## 4.5 页面 E：掌握度报告

### 页面目标

让结果可复盘、可分享、可继续学习。

### 报告结构

```text
本次掌握度                    91%
补讲前 72%  ───────────────→  补讲后 91%

准确覆盖       6 / 8
需要修正       1 处
关键遗漏       2 处
观点差异       1 处

你已经掌握：……
下一步建议：……
仍需验证：……

[生成知识卡片] [再考一次] [复制分享]
```

### 知识卡片字段

1. 问题；
2. 一句话结论；
3. 关键条件；
4. 常见误区；
5. 不同答主的观点；
6. 我的最终理解；
7. 知乎来源列表。

---

## 4.6 页面 F：从 0 掌握 / 入门地图

### 页面目标

为零基础用户提供一份由实时知乎资料生成的最小可学路径，并通过复述把“看懂”转化为“会讲”。

### 交互

- 后端并行调用 `search zhihu` 与 `answer`；
- 展示 5～8 个由浅入深的知识点，每个点包含定义、通俗解释和可选例子；
- 展示常见误区和一个自测问题；
- 用户输入至少 30 字的复述后，调用 `/api/evaluate` 进入标准比对页；
- 入门地图中的搜索摘要展示真实知乎链接，直答内容标注“知乎直答入门指南”。

### 页面字段

```json
{
  "overview": "这个主题是什么，为什么值得了解",
  "key_points": [{"title":"概念","explanation":"通俗解释","example":"例子"}],
  "misconceptions": ["常见误区"],
  "starter_question": "请用自己的话回答"
}
```

## 4.7 页面 G：实时服务异常

### 页面目标

让用户知道“发生了什么、是否需要修改输入、下一步能做什么”，避免把接口故障误认为知识判断。

### 状态与动作

| 状态 | 用户看到的提示 | 可执行动作 |
|---|---|---|
| 未配置凭证 / CLI 不可用 | 知乎服务尚未连接，本轮无法开始评估 | 检查服务端配置；保留当前讲述 |
| 搜索超时或服务错误 | 知乎搜索暂时不可用 | 重试一次或改写主题 |
| 直答超时或返回格式异常 | 知乎直答暂时不可用 | 重试一次；不展示半成品评分 |
| 搜索无结果 | 没找到足够相关的知乎内容 | 缩短问题、去掉背景描述后重新提交 |
| 配额 / 频率限制 | 本轮额度暂时不可用 | 停止自动重试，稍后再试 |

异常状态必须保留用户已输入的主题和讲述；不使用本地 fixture 填充结果，也不显示底层 Access Secret、命令行输出或堆栈信息。

## 6. AI 评估逻辑

### 6.1 处理管线

```text
知乎检索结果
   ↓
去重、截断、来源标准化
   ↓
关键点抽取（结论 / 条件 / 例子 / 反例）
   ↓
用户讲述切分为主张
   ↓
主张 ↔ 关键点匹配
   ↓
判断标签 + 证据句 + 修正建议
```

### 6.2 评分建议

每个关键点 0～2 分：

- `2`：结论和关键条件基本准确；
- `1`：方向正确，但缺少条件或例子；
- `0`：明显冲突、概念混淆或完全未覆盖。

总分示例：

```text
基础掌握度 = 已覆盖关键点得分 / 全部关键点满分 × 100%
补讲加分 = 仅对补讲前为 0 或 1 的点重新计算
最终掌握度 = 补讲后得分 / 全部关键点满分 × 100%
```

### 6.3 结构化输出格式

```json
{
  "topic": "AI 会不会替代初级程序员？",
  "score_before": 72,
  "score_after": 91,
  "items": [
    {
      "status": "correction",
      "user_claim": "...",
      "assessment": "因果关系说反了",
      "explanation": "...",
      "source": {
        "title": "回答标题",
        "author": "作者名",
        "url": "https://www.zhihu.com/...",
        "quote_or_summary": "接口真实返回的原文片段或回答摘要"
      },
      "repair_prompt": "请补充说明……"
    }
  ]
}
```

### 6.4 提示词约束

系统提示词应明确：

- 只能根据检索到的知乎内容判断，不得编造来源；
- 区分事实冲突、概念混淆、关键遗漏和观点差异；
- 不能把个人经验写成普遍事实；
- 只有真实搜索返回的片段才能作为原文证据；拿不到正文时标注“回答摘要”，不得伪造逐字引文；
- 没有足够证据时使用“可能遗漏”或“观点不同”，不要武断判错；
- 直答负责输出判断，来源 URL 由后端从真实搜索结果中匹配；匹配不到时 URL 留空并明确提示“未返回可验证链接”。

## 7. 知乎能力接入建议

### 7.1 MVP 调用组合

- `search zhihu`：按主题检索相关回答、文章和经验，作为可追溯来源；
- `answer`：调用知乎直答生成结构化考点与反馈，模型默认 `zhida-thinking-1p5`；
- `search global`、`question answers`、`hot`：作为后续版本能力，只有产品新增入口时再接入，不在 MVP 中暗示已支持。

### 7.2 请求策略与错误态

- 搜索与直答并行发起，单次提交只发起一轮请求；补讲只复测选中的知识点；
- 不对直答失败做自动重试，避免重复消耗额度；用户可主动点击重试；
- 主题失败时显示：`知乎内容暂时不可用，请稍后重试`，保留用户讲述内容；
- 结果为空时引导用户改写主题，不反复重试；
- 页面显示“来源类型”：真实搜索摘要 / 知乎直答综合说明；不把直答说明标成答主原话。

### 7.3 运行前提与配额提示

- 后端启动时通过知乎 Skill 的 `run.ps1 status` 自动发现 CLI，并从当前进程环境变量读取 `ZHIHU_ACCESS_SECRET`；凭证只存在于服务端。
- 搜索、评估和补讲复测均为实时请求，分别可能消耗知乎搜索与直答额度；MVP 不做无意义重试。
- 未配置凭证、CLI 不兼容、超时、限流和空结果都进入可恢复错误态，不展示猜测内容。
- 页面可提示“本轮使用知乎搜索与知乎直答”，但不展示 Access Secret 或底层诊断信息。

### 7.4 归属与合规

- 保留作者名、标题和知乎原文链接；
- 不把 AI 改写内容标成答主原话；
- 认证、赞数等字段只有接口真实返回时展示；
- 不在前端、日志、仓库和演示视频中暴露 Access Secret、OAuth Token 等凭证；
- 明示：**高赞回答代表社区观点，不等于绝对事实。**

## 8. 技术架构（适合黑客松）

```text
前端（原生 HTML / CSS / JavaScript）
  ├─ 选题与讲述
  ├─ 比对卡片
  ├─ 补讲与报告
  └─ 刘看山状态组件
          ↓
后端 API（Node.js 标准库）
  ├─ Skill CLI Resolver：status 发现官方 zhihu-cli
  ├─ Live Search Adapter：search zhihu
  ├─ Direct Answer Adapter：answer（zhida-thinking-1p5）
  ├─ Content Normalizer：统一搜索与直答字段
  └─ Error Boundary：超时、鉴权、限流、空结果 → 502/可重试
          ↓
前端知识点绑定
  ├─ 主题相关性过滤
  ├─ 知识点与搜索摘要匹配
  ├─ 四类状态统计与评分
  └─ 补讲复测与报告
```

### 推荐接口

```text
POST /api/search        # 真实知乎搜索
POST /api/evaluate      # 知乎直答结构化评估
POST /api/reteach       # 知乎直答针对单点复测

> 带持久化的 `/api/session`、历史报告和登录能力属于后续版本；当前 Demo 使用浏览器内存保存单次会话。
```

### 会话状态

```text
draft → submitted → researching → evaluated → reteaching → completed
```

## 9. 90 秒路演脚本

### 0～10 秒：提出问题

“我们都经历过：看完一篇知乎高赞回答，觉得自己懂了，但让你解释时却讲不清。”

### 10～20 秒：产品亮相

“这是答主考官。你先讲一遍，知乎社区真实内容来考你。”

### 20～40 秒：用户讲述

选择“AI 会不会替代初级程序员”，现场输入一段有明显缺漏的回答，点击提交。

### 40～65 秒：答主比对

展示 3 张卡片：

1. 一条“准确覆盖”；
2. 一条“因果关系说反了”，展开来源片段；
3. 一条“关键遗漏”，显示答主反复强调的适用条件。

### 65～78 秒：补讲

用户补充“规则清晰、可拆分的任务更易被自动化”，该点从“需要修正”变成“已掌握”。

### 78～90 秒：结果收束

展示 `72% → 91%`，生成带知乎来源的知识卡片。

收尾句：

> “知乎让我们看见真实经验，答主考官让我们证明自己真的理解了。”

## 12. 后续版本

第一版验证“主动讲述 + 社区校验”是否成立；在实时链路稳定后可扩展：

- 个人学习档案与间隔复习（需要会话持久化与登录）；
- 收藏夹自动生成主题课程；
- 多答主观点地图；
- 面试 / 答辩专用考官模式；
- 语音表达质量与逻辑结构反馈；
- 将最终知识卡片发布为用户自己的创作草稿。

### 12.1 明确的产品边界

- 知乎直答是“基于检索资料的综合说明”，不是某位答主的原话，也不能替代原始搜索结果。
- 搜索摘要是服务返回的摘要，不等于完整回答全文；展示时必须保留知乎链接与作者字段（仅在接口真实返回时展示）。
- 高赞、热榜或单条搜索结果只代表社区观点或当前热度，不能单独作为事实裁决。
- 任何无法由实时接口证明的内容，都应标记为“待验证”或不展示，而不是用本地 fixture 补齐。

**核心原则不变：先让人思考和表达，再让 AI 借助知乎真实知识帮助他修正。**
